# Геймдизайн, баланс и генерация — исследование для конструктора

Опора для задач Леона (механики), Васи и Дани (ML/баланс). Правила для кода — скилл `game-engine`, эталон механики — `docs/legacy/NEUROFAUNA_RULES.md`.

## 1. Зачем игра в учебной смене — что говорят данные

- **Мета-анализ Sailer & Homner (2020, Educational Psychology Review)**: геймификация даёт значимые положительные эффекты на когнитивные (g = 0.49), мотивационные (g = 0.36) и поведенческие (g = 0.25) результаты. Когнитивный эффект устойчив в методологически строгих исследованиях.
- Для поведенческих результатов особенно работают **игровой сюжет (game fiction)** и **конкуренция в сочетании с кооперацией**. Это ровно формат брифа: команды соревнуются друг с другом, внутри команды сотрудничают, прямой конфронтации нет.
- Мета-анализ по высшему образованию (2026) даёт больший эффект, но с огромной гетерогенностью (I² ≈ 99%). Качество дизайна важнее самого факта игры.
- Гибридные «физическое поле + приложение» форматы удерживают мотивационные плюсы настольной игры и решают проблему учёта прогресса. Приложение — бухгалтерия и прозрачность, а не замена живой игры.
- Риск: геймификация ради развлечения, без связи с учебными целями. **Вывод для конструктора:** валюта должна начисляться только за учебные действия, а причины начислений — быть частью шаблона (`rewardReasons`) и привязываться к дисциплинам STEM.

## 2. Требования брифа → требования к ядру

| Требование | Следствие для ядра |
| :--- | :--- |
| ≥3 дней, 3–4 действия команды в день | шаблон задаёт `totalDays`, `actionsPerDay`; симуляция работает в этих единицах |
| Конкуренция без конфронтации | эффекты не бьют по другим командам напрямую; catch-up — только «догоняющие» бонусы (как «Стайное») |
| Гибрид: экономика в боте, ходы — в реальности | ядро считает исход хода по входу «команда встала на клетку X»; поле — данные шаблона |
| STEM в центре | статы, слоты и причины начислений мапятся на дисциплины S/T/E/M; генератор получает это как ограничение |
| ≥2 механики + 1–2 дополнения | механика = модуль ядра (свой стейт, свои действия и эффекты), а не ещё один пресет-тема |

### Кандидаты во вторую механику (на обсуждение с Леоном и заказчиком)
1. **Исследовательское дерево (tech tree)**: вместо слотов — граф технологий, открытие узла требует валюты и предпосылок. Подходит под инженерные смены (дирижабль, робот).
2. **Контракты/заказы**: общий пул заданий с требованиями к статам. Команда выполняет заказ сборкой и получает трек и валюту. Работает без физического поля, полезно для коротких событий.
3. **Ресурсный движок (engine building)**: карты приносят доход каждый день. Уже частично есть в оригинале через «Доминирующее».

Дополнения (add-ons): событийные карты дня; командные достижения (бейджи за учебные цели); сезонный модификатор правил на день.

## 3. Баланс: что проверять

**Статический анализ** (уже есть в `validateGameBalance`): эффективность «сумма статов / цена» по дням, покрытие слотов, пустые дни. Ограничение: не видит взаимодействий перков, порогов клеток и экономики во времени.

**Симуляция (следующий шаг).** Monte Carlo-прогоны смены агентами с разными стратегиями. Ключевой урок из практики: симуляция отвечает только на точно поставленные вопросы. Она проверяет баланс и эксплойты, но не «весело ли». Метрики:

| Метрика | Цель (гипотеза, уточнить на плейтестах) |
| :--- | :--- |
| Доля побед каждой стратегии (speed/strength/survival/mixed/perk-rush) | ни одна не выше ~35–40% при 4–6 стратегиях |
| Лидер в середине смены выигрывает | < 60–65% (иначе runaway leader) |
| Разброс финальных позиций | не все финишируют на 30 к 3-му дню и не все < 15 к 5-му |
| Приток валюты за день vs стоимость полной сборки | полная «идеальная» сборка недостижима раньше предпоследнего дня |
| Используемость карт | каждая карта покупается ≥ x% прогонов; иначе мертва или переоценена |
| Чувствительность | ±1 к цене/порогу не переворачивает рейтинг стратегий |

**Runaway leader и catch-up.** Положительная обратная связь (больше статов → больше валюты → больше статов) — главный риск гонки. В оригинале есть встроенные амортизаторы: «Стайное» (+2 при ≥3 командах впереди), штрафы с откупом. Конструктор должен измерять долю побед лидера середины смены и давать рычаги настройки (бонусы догоняющим, кривая сложности клеток). Пологий рост сложности даёт отстающим шанс; слишком лёгкая фаза в конце превращает игру в лотерею.

## 4. Генерация шаблонов (ML)

Рабочий конвейер (паттерн «schema → domain checks → bounded repair»):

1. **Вход организатора**: тема, аудитория, длительность, число команд, дисциплины, выбранные механики и дополнения.
2. **Генерация** LLM со structured output по JSON Schema из `GameTemplateSchema` (`z.toJSONSchema`). Strict-режим провайдеров требует все поля required: опциональное делаем `nullable`.
3. **Валидация**: Zod (собираем все ошибки разом, не fail-fast) → ссылочная целостность → `validateGameBalance` → симуляция.
4. **Repair-loop**: ошибки валидации и метрики симуляции возвращаются модели, не больше 2–3 итераций, затем ручная правка.
5. **Детерминированный ребаланс** поверх LLM: числа (цены, пороги) лучше подбирать поиском или оптимизацией по метрикам симуляции, а LLM оставить тексты, темы и структуру.

Исследования: LLM-генерация карточек (Pokémon-кейс, 2026) оценивалась людьми, а не симуляцией. Работы по PCG+симуляциям (AIIDE 2025, FDG 2025) подтверждают подход «агенты + метрики win-rate», но для карточных игр это открытая задача. Валидатор с симуляцией — реальная ценность конструктора, а не сама генерация названий (совпадает с выводом встречи 2026-10-01).
